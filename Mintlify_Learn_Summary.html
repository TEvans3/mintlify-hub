Structure Docs That Scale
4 lessons · Why most documentation problems are structure problems, not writing problems — and how to fix them.
L1 Understand your readers first
Audience clarity is the foundation of every structural decision. "Developers" isn't specific enough — you need a concrete reader definition: role, goal, and prior knowledge.
A new integrator, a returning API user, and a tech lead evaluating your product are three different readers — serving all three equally serves none well.
Structure is downstream of audience. The same information needs different organization depending on who's reading it.
Mintlify's approach: define the primary reader in a CLAUDE.md or Cursor rules file — so AI writing tools always have context before touching your docs.
Sales translation
Most engineering leaders think their docs problem is a content quality problem. It's not — it's an audience clarity problem. Their docs are structured around their product, not around what their developers actually need to do. That's the reframe.
L2 Choose the right content type
Every page should be one of four types (Diátaxis framework): Tutorial (learn by doing), How-to guide (complete a task), Reference (look up info), or Explanation (understand a concept). Mixing types on one page is one of the most common reasons docs become hard to navigate.
Each type has a different structure, assumed knowledge level, and relationship to adjacent pages.
Mixing types breaks the contract with the reader: they came to do something and ended up reading an essay.
AI tools default to hybrid content — explicit type instructions in CLAUDE.md prevent this drift.
Sales translation
When you audit a prospect's docs and see pages doing five jobs, you can name it: "This is a content type problem — your engineers land on a page expecting steps and get a concept essay, or vice versa. That's the friction that drives support tickets."
L3 Design navigation for your users (not your product)
Most docs navigation mirrors the product's architecture — not what users are trying to accomplish. Users navigate by goal, not by feature.
Feature-based nav: "Sources / Destinations / Transformations." Goal-based nav: "Get started / Connect your data / Transform and model." Same content, opposite usability.
Mintlify primitives: Groups (same purpose), Tabs (different audiences or use cases), Products (separate product lines), Anchors (globally useful resources).
Name sections for what users accomplish, not what the section contains. "Webhooks" vs "Receive real-time events."
Sales translation
Ask a prospect to show you their docs nav and ask: "If I'm a developer who just signed up and wants to make my first API call, where do I click?" Their hesitation tells you everything about what their docs are actually costing them.
L4 Keep docs accurate as your product grows
Documentation goes stale by default. The fix is process, not effort. The most effective habit: docs changes ship in the same pull request as the feature they document.
Docs-as-code: version-controlled, reviewed via PR, deployed through a pipeline. This is what Mintlify is built on.
Mintlify's agent watches the product repo and auto-drafts doc updates when code merges — removes the blank page problem, not the human review step.
Wrong documentation is worse than no documentation. A page describing a workflow that no longer exists costs users more than a 404.
Maintenance rhythm: update with every release, review AI assistant conversations monthly, audit high-traffic pages quarterly.
Sales translation
This is where you quantify the Coinbase stat (doc updates: 20 min → 60 sec). The before state isn't laziness — it's structural. Docs and code live in different systems, so they drift apart by default. Mintlify closes that gap architecturally.
Create Agent-Friendly Docs
4 lessons · Your documentation now has two audiences — humans and AI agents. Here's how to serve both, and why the same fixes help both.
L1 How agents read your documentation
Agents process docs as isolated text chunks — without session memory, without navigation context, without knowing what's adjacent. They fetch a page and work with what they find there.
Pages must be self-contained. "As described in the previous section" is invisible to an agent — it may only have that one page.
Metadata matters: vague titles like "Advanced configuration" tell agents almost nothing. "Configure rate limits for API requests" matches real user queries.
Terminology inconsistency silently breaks agents — "workspace" and "organization" used interchangeably means agents treat them as different concepts.
Technical failures cause silent errors: pages over ~50K chars get truncated (agent doesn't know), tabbed content hides all but the first tab, JS-rendered content returns nothing.
Sales translation
This is the AI readiness argument. If your docs aren't structured for agent consumption, your AI strategy built on top of them will produce wrong answers at scale — with no error message, just silent failures. That's a board-level risk.
L2 Write content agents can use
Specific writing habits that make docs reliable context for agents (and better for humans too): self-contained pages, specific titles and descriptions, standalone headings, consistent terminology, complete runnable examples.
Weak description: "Learn about our authentication system." Strong: "Authenticate API requests using API keys. Covers generating keys, passing them in headers, and handling 401 errors."
Phrases like "the above," "as mentioned," and "it will return" create ambiguity humans resolve through context — agents often can't.
Code examples must be complete and runnable. Agents surface them to answer questions; a broken example means a wrong answer delivered with full confidence.
Sales translation
The developer who hits a broken example in your docs doesn't file a ticket — they leave. The AI agent who hits a broken example gives them a confident wrong answer. Both outcomes destroy developer trust.
L3 Control what agents see — the four key files
Configuration files determine what agents know about your product beyond what's in individual pages.
llms.txt — Curated index of your docs for agents. Mintlify auto-generates one. Strong version has a product description, page descriptions, logical ordering. Exclude changelogs, deprecated content, blog posts.
CLAUDE.md — Read by Claude Code before editing your repo. Define audience, canonical terminology, content type rules, style conventions. Shapes every AI-assisted edit.
AGENTS.md — Same purpose as CLAUDE.md but read by OpenAI Codex and other coding agents. Maintain both if your team uses multiple AI tools.
SKILL.md — Packages step-by-step instructions for agents to discover and invoke specific capabilities in your product's API.
Sales translation
llms.txt and CLAUDE.md are the infrastructure that makes your docs AI-native — not just AI-generated content, but docs that are structurally readable by the models developers are building on. Anthropic co-developed the LLMs.txt standard with Mintlify. That's the moat.
L4 Keep content agent-friendly over time
Agent-friendliness degrades the same way accuracy does — product changes without doc updates. Agents present stale information with the same confidence as current information.
Use your own AI assistant as a feedback loop — ask it questions about your product and see where it fails. Failures are documentation gaps.
Terminology drift is the silent killer — as teams grow, different contributors use different names for the same concept. Periodic audits with a canonical style guide prevent it.
Review llms.txt whenever major sections are added or removed — it's a snapshot, not a live feed unless auto-generated.
Sales translation
Most teams think they'll fix their docs "later." The maintenance model here makes "later" unnecessary — if the process is right, the docs stay current automatically. That's the pitch against the status quo.
Git & GitHub for Mintlify
8 lessons · Why engineering documentation teams work in Git, how the docs-as-code workflow operates, and why it matters for a $150k enterprise sale.
L1–2 Why docs teams use Git + core concepts
Git is version control: tracks every change, who made it, when. For documentation: complete history, parallel work without overwriting each other, review before publishing.
Key concepts: Repository (your docs project), Branch (isolated copy for changes), Commit (saved snapshot), Pull Request (proposed change pending review), Merge (change goes live).
Mintlify's docs-as-code approach treats documentation with the same collaboration and quality standards as software — this is a quality philosophy, not just a technical choice.
Sales translation
When a VP of Eng asks "how do we control what goes into our docs site?" — this is the answer. Every change is a PR. PRs have reviewers, automated checks, and preview deployments. This is the governance model engineering orgs already understand and trust.
L3–4 Get connected + access & permissions
Mintlify connects directly to your GitHub or GitLab repository. Two permission layers: GitHub controls repository access (who can push code), Mintlify controls site configuration.
Mintlify installs as a GitHub App — no separate infrastructure to manage. The integration is the product.
Access model maps cleanly onto how engineering orgs already manage permissions — IT and security teams will recognize this pattern immediately.
Sales translation
This is your answer to the InfoSec question. The permission model extends the permissions your engineering org already controls in GitHub. No new vendor access surface to audit.
L5–6 Workflow overview + branch best practices
Two ways to edit: web editor (Mintlify handles Git behind the scenes) and local CLI editing (full control). Most teams use both.
Web editor workflow: edit → publish → Mintlify creates branch, commits, opens PR automatically → review preview → merge → live.
CLI workflow: pull latest → branch → mint dev for local preview → commit → push → PR → merge → live.
The core habit: docs changes ship in the same PR as the feature they document. This is what prevents drift structurally, not through process discipline.
Sales translation
"Your engineers already know this workflow. They do it for code every day. Mintlify makes docs part of the same motion — not a separate system that runs on someone's goodwill." This is how you counter the Confluence inertia argument.
L7–8 Preview deployments + team collaboration
Every pull request gets an automatic live preview deployment of the entire docs site with proposed changes applied.
Mintlify's GitHub app runs automated checks on every PR: broken links, missing metadata, style/spelling (via Vale). Problems surface before users see them.
Writers, engineers, and product managers can all contribute via branches without stepping on each other.
Preview deployments are the quality gate — changes reviewed in context, not in a diff view that requires imagination.
Sales translation
This is the DevRel champion's argument to their VP of Eng: "Every docs change goes through the same review process as code. No more rogue updates, no more broken pages discovered by external developers. The quality bar is enforced by the system."
How to Use Mintlify Components
16 lessons · The component library that turns good content into great developer experience — and what over-use looks like.
Callouts Note / Warning / Tip / Info — when each applies
Callouts interrupt reading — use them only when the interruption is worth it. Each type sends a specific signal: Note (supplementary context), Warning (consequence of getting this wrong), Tip (faster alternative), Info (background the reader may need).
Callout fatigue is real: when every page has 5 callouts, readers stop reading them. Warning callouts lose their meaning when they appear 3× per page.
If the information is important enough to interrupt the reader, it's probably important enough to be in the main prose.
Sales translation
Callout overuse is a visible quality signal you can point to in a prospect's existing docs. "When everything is a warning, nothing is a warning — your developers learn to skip them, which means they miss the ones that matter."
Steps & procedures Steps vs numbered lists, branching, complex flows
Steps component vs plain numbered lists: Steps support richer content — code blocks, images, sub-steps — within each step.
Use Steps when each step contains multiple elements. Use numbered lists when each step is a single sentence.
Branching procedures should fork at the decision point — not run as two separate complete guides that drift apart over time.
When a procedure outgrows a page, split it into linked focused pages rather than scrolling further.
Sales translation
Complex procedures that sprawl across one page are a leading cause of "developers gave up and filed a support ticket." This is where you connect docs quality directly to support ticket deflection rates.
Code Code blocks, code groups, inline explanation
Code blocks should specify language (for syntax highlighting), title (for context), and line highlights (for focus). Code groups show the same example in multiple languages without repeating prose.
How much prose around a code block depends on content type and audience. Reference pages: minimal prose. Tutorials: step-by-step explanation.
Code groups prevent the "same example, 5 tabs of repetitive prose" pattern — the most common cause of bloated API docs.
Sales translation
Your buyer's external developers will judge your customer's product by the quality of the code examples in their docs. A broken example is a lost integration. A language-toggled code group that just works is a converted developer.
Navigation & comparison Tables, cards, tabs, conditional content, end-of-page
Each component signals a different thing to the reader. Tabs: same content, different contexts. Tables: structured comparison where relationships matter. Cards: navigation anchors or bounded objects.
Tabs hide content from agents (only the first tab is visible) — critical AI readiness consideration from Course 2.
End-of-page navigation components determine whether a developer continues their journey or exits — arguably the highest-leverage page element for adoption.
Conditional content (the View component) shows or hides sections based on user selections — keeps one page serving multiple audience segments without fragmentation.
Sales translation
End-of-page navigation is where developer adoption either continues or stops. Mintlify's component system makes this intentional rather than accidental — your customer's docs stop being a dead end and become a guided journey.
Discovery Questions — Product-Informed
Questions drawn directly from Mintlify Learn course concepts — mapped to MEDDPICC categories and Challenger intent. These are different from the standard question bank: they're sharper because they come from product fluency, not just sales frameworks. Use to diagnose, not interrogate.
Identified Pain — surface the structural problem
"When one of your developers hits a documentation page looking for how to do something specific — how often do they find what they came for versus having to dig, ask a colleague, or file a ticket?"
Surfaces the navigation and content type mismatch problem. Engineers answer this honestly because they live it daily.
"Walk me through what happens between a feature shipping and the docs for that feature going live. Who owns that, and what's the typical lag?"
Diagnoses docs-as-code gap. The answer almost always reveals a separate process that runs after engineering — which is where drift starts.
"If I open your docs and search for something your product does — can I find the answer in 30 seconds, or does it require me to already know where to look?"
Mintlify's navigation lesson made concrete. If they pause, you've identified the pain without them having to admit it.
"How much engineering time per week would you estimate goes into maintaining documentation versus building product — and does that feel like the right ratio?"
Connects to the HubSpot 50% headcount reduction proof point. Gets the Metrics conversation started.
"What happens to your docs when a feature gets renamed, or a workflow changes significantly? What's the process for catching every page that needs updating?"
Exposes terminology drift and the absence of automated checks. The answer is usually "someone tries to remember" — which is not a process.
AI readiness — the forward-looking reframe
"Your developers are probably already using Claude Code, Cursor, or similar AI coding agents. When those agents try to use your documentation as context — how confident are you that they're getting accurate answers?"
Opens the agent-friendly docs conversation. Most VPs of Eng haven't thought about this yet. That's the Challenger reframe — they have a problem they don't know they have.
"When ChatGPT or another LLM answers a question about your API — where do you think that answer is coming from, and how confident are you it's accurate?"
Surfaces the AI readiness liability. If their docs aren't structured for agent consumption, the LLM is either hallucinating or returning stale information.
"You mentioned you're building [AI initiative]. What's the knowledge base those models will be trained on or querying — and is that content structured in a way that LLMs can actually use?"
Connects Mintlify's AI-native architecture (llms.txt, MCP servers) to a live AI initiative. Makes the documentation problem a blocker for something they're already trying to do.
Technical workflow — understand their current state
"Where does your documentation actually live right now — is it in the same repository as your code, or in a separate system like Confluence or Notion?"
Identifies whether they have docs-as-code or a siloed system. The answer determines how you frame the migration conversation.
"When a developer opens a PR for a new feature — does that PR include the documentation for that feature, or does docs happen separately after the fact?"
The single most diagnostic question for docs drift. Almost no one ships docs in the same PR as the feature before Mintlify.
"How does your team currently review documentation changes before they go live — is there a PR process, or does someone publish directly?"
Surfaces the quality control gap. For regulated industries, connects to compliance and audit trail needs.
"Do your technical writers and engineers work in the same toolchain for documentation, or are they in different systems that have to be synced?"
Diagnoses the collaboration fragmentation that causes both drift and quality inconsistency.
Developer adoption — the external impact
"When external developers integrate your API — what's the most common reason they file a support ticket in the first 30 days?"
Connects docs quality to support ticket volume. If the answer involves "couldn't find" or "docs were wrong" — you have a quantifiable Metric.
"If I'm a developer evaluating your API against a competitor's — what does your docs experience tell me about your product's quality? Is that the first impression you want to make?"
Connects developer experience to competitive positioning. Developer-facing companies often underestimate how much docs quality influences API adoption decisions.
"What percentage of developers who start integrating your API actually complete the integration — and do you have a sense of where the drop-off happens?"
Surfaces the adoption funnel impact. Documentation friction is often the invisible cause of developer drop-off that nobody has quantified.
Economic Buyer + compelling event
"When you think about the cost of your current docs setup — engineering time maintaining it, developer adoption that doesn't happen, support tickets from documentation gaps — has that been quantified anywhere, or is it mostly felt?"
Sets up the Metrics conversation with the EB. "Mostly felt" is the gap you fill. If they have a number, that's your anchor.
"Is there a product launch, API expansion, or engineering initiative coming up in the next quarter where the quality of your documentation will directly affect the outcome?"
Surfaces the compelling event. This is the Why Now question asked in developer-org language.
"Who in your organization would feel the most pain if your developer documentation caused a major API integration failure or a significant developer experience incident?"
Maps to Economic Buyer. The answer is usually CTO, VP Eng, or VP Developer Experience — whoever is accountable for developer adoption metrics.
